⚠️ 核对过程中发现两个真实缺陷（与本次调研无关，但更紧急）

① 限流误判（已修 923ff0d）：错误码 40001 被当裸字符串搜整页正文， 命中了显卡型号 RTX A4000 16G 的标题 —— 今天误熔断 2 次，每次中止整批并推进退避阶梯。
② 万元价丢失（已修 7f8fccb）：闲鱼把 2.30万 拆成三行渲染 （¥ / 2 / .30 / 万），提取器只取「¥ 的下一行」→ 记成 ¥2.00 后被数据质量闸门丢掉，净效果是所有万元级二手报价被静默丢弃。
两者的完整证据链见 第 09 / 10 节。

结论速览
  1. 最大的优化空间在「取数方式」，不在「反爬对抗」。我们三个源都在解析 innerText；而这些平台自己就发结构化 JSON（闲鱼 MTop、拼多多 apiv3.yangkeduo.com），浏览器已经收到过——我们只是没接。
  2. 拼多多的 anti-content 不要去逆向。公开的破解产物（3720 行反混淆 JS + 补环境）是 2022 年的，已明显过期；现在通行的做法是让浏览器自己签名。
  3. 闲鱼是单轮耗时的大头（约 85%）。今日实测 15 个型号耗时 390s / 411s（26~27s/型号），其中相当部分是为了"看起来像人"而付出的页面渲染成本。
  4. 我们已经在若干维度上领先于这些项目。指纹七组对照实测、熔断跨进程持久化、单会话任务上限、磁盘冷启动清理、数据口径闸门——调研的 10 个项目没有一个全都具备。
  5. 代理池与多账号轮换：建议不做。理由不是"做不到"，而是我们带登录态且目标是国内站，境外 IP 会直接触发风控的账号盗用判定。
  6. 从它们代码里可提炼出值得做的共 14 项（另有 2 项有条件、7 项明确不做）——完整编号清单见第 08 节。

02四条技术路线

路线 A HTTP API + 签名

直接调平台的 H5 接口，自己算签名。代表：superboyyy/xianyu_spider。

  • 速度极快、拿的是结构化 JSON
  • 签名一旦改版就要重写
  • 需要自己维护 Cookie / token 生命周期
路线 B JS 逆向 + 补环境

把加密 JS 抠出来反混淆，用 Node/PyV8 在补好的浏览器环境里跑。代表：Crack-JS-Spider、JDPackage。

  • 无浏览器，资源占用最低
  • 维护成本最高，每次改版要重新逆向
  • 产物易过期（样本已过期 3 年）
路线 C 浏览器 + MITM 代理截获

浏览器正常访问，本地代理截获它的 API 响应。代表：SZFsir/pddSpider（还顺手改写了 JS 剥掉 navigator.webdriver）。

  • 不碰 DOM、不碰签名
  • 拿结构化数据，对页面改版免疫
  • 代理层要自己维护
路线 D 浏览器当"签名机"

开一个官方页面，调用它页面内的原生签名函数，再走 HTTP 取数。代表：LittleCrawler 的 playwright_sign.py。

  • 不逆向、不补环境，签名永远是最新的
  • 速度接近路线 A
  • 保留一个浏览器上下文

路线 C/D 的关键代码证据

这两条路线最值得借鉴，摘录其原始实现：

03逐项目剖析

① superboyyy/xianyu_spider — 闲鱼 API 直连（与本项目同平台，最值得细读）

它的搜索不走浏览器。浏览器（Playwright）只在扫脸认证时用一次；日常搜索是 httpx 直连 MTop 接口。 
# xianyu/mtop.py（已核对原文）
BASE_URL = "https://h5api.m.goofish.com/h5/{}/1.0/"
APPKEY   = "34839810"
SEARCH_API = "mtop.taobao.idlemtopsearch.pc.search"     # 注意：pc.search —— 就是 PC 网页调的那个接口

def generate_sign(token, appkey, data, j):
    # sign = md5(token & 时间戳毫秒 & appkey & 紧凑JSON(data))
    return md5(f"{token}&{j}&{appkey}&{json.dumps(data,separators=(',',':'))}")

def _h5_token():
    # token 就是 _m_h5_tk Cookie 的前半段
    return _cookie_value("_m_h5_tk").split("_")[0]
token 怎么来的：先带 token="undefined" 请求一次"公告页"接口（mtop.gaia...index.get），响应里下发 _m_h5_tk Cookie，之后每次请求用它签名。
token 过期怎么办：响应 ret 含 TOKEN_EXPIRED 或 FAIL_SYS 时，重新走一次上面的取 token 流程，然后重试一次 —— 只重试一次，不循环。
登录态失效怎么办：清掉登录 Cookie，但保留 _m_h5_tk / _m_h5_tk_enc / cna 三个匿名 Cookie，搜索按未登录继续，结果里标 login_expired。这个"降级而不失败"的设计值得抄。

② pbeenigg/LittleCrawler — 工程化最完整的一个

它是唯一同时具备"CDP 浏览器管理 + 代理池 + 缓存抽象 + 签名模块 + REST API + Web UI"的项目。最值得看的是 cdp_browser.py 与 playwright_sign.py。

模块它的做法对我们的参考价值
playwright_sign.py用 page.evaluate("window.mnsv2(...)") 借页面签名高 —— 拼多多 anti-content 的正解
easing.py + slider_util.py缓动函数生成滑块轨迹（ease_out_expo 等）低 —— 我们明确不做滑块脚本化
cdp_browser.pyCDP 连接已有浏览器、可复用 context、stealth.min.js 注入中 —— 与我们的 session 层同类，但我们的更贴合 macOS
proxy_ip_pool.py多供应商（极速/快代理/豌豆）统一抽象 + proxy_mixin 混入低 —— 见第 05 节"不做代理池"
services/cache/本地 / Redis 双实现的抽象层中 —— 可参考其"抽象 + 工厂"的写法

⑤ SZFsir/pddSpider — 已失效，但留下最有价值的一条思路

作者自己在 README 里写明："我的代码已经被拼多多的反爬策略过滤了"。他们的应对手段是双重的：① MITM 代理读 API 响应；② 运行时改写 JS，把 navigator.webdriver 替换成随机名。 
# Spider.py —— 在代理层改写回包里的 JS
if 'react_psnl_verification_' in response.request.path:
    js_body = response.get_body_data().decode()
    js_body = js_body.replace("navigator.webdriver", "navigator.qwerasdfzxcv")
    response.set_body_data(bytes(js_body, 'utf-8'))
关于这个技巧的评价：它针对的是 Selenium 驱动的浏览器（Selenium 会注入 navigator.webdriver=true）。我们不是 Selenium，也不是 Playwright 的 launch()——我们是自己 Popen 启动普通 Chrome 再用 CDP 连接，本来就没有这个特征。所以这个技巧对我们无收益（详见第 05 节）。但它验证了一件事：网络层才是数据的可靠通道。

04与我们的对照

下表把我们现有实现与调研结论逐维度对照。绿=我们更强，红=存在明确改进空间。

维度我们现在的做法开源项目的普遍做法 / 差距
取数方式 DOM 解析：京东用 locator('[class*="goodsCardWrapper"]')；拼多多/闲鱼用 page.evaluate() 拆 innerText 行 主流是读网络层：MITM 代理截 API 响应（路线 C）或直接调 API（路线 A）。对页面改版免疫，且能拿到 DOM 上根本看不到的字段
签名处理 不处理 —— 让浏览器自己发请求，签名天然正确 逆向（易过期）或"借浏览器签名"（路线 D）。我们的选择是对的，但代价是必须等整页渲染
反指纹 已实测七组对照（真实页面卡片数 + 风控判定），明确拒绝 headless / 拦图片 / 关 GPU，并记录了每项的实测数据 普遍是"凭经验加一堆参数"，没有任何一个项目给出对照实测数据。LittleCrawler 加了 --no-sandbox（Linux 习惯）与 AutomationControlled 补丁，对我们是负收益
节奏控制 平台差异化：高斯扰动 + 上下限夹取 + 长停顿概率，三平台各不相同 多数是固定 sleep 或 random.uniform；ShilongLee 的京东搜索完全没有间隔控制
熔断 平台粒度 + 跨进程持久化（data/breaker.json）+ 软/硬双阶梯 基本没有熔断。有熔断的（ShilongLee）是账号粒度且仅内存态
会话生命周期 单会话任务上限 + 频次/时长双重回收 + 轮次结束彻底关闭浏览器 普遍是"一个浏览器跑到底"，或常驻浏览器不关
磁盘治理 磁盘缓存外置到临时目录 + 每轮清理 profile 白名单子目录 10 个项目没有一个做这个。长期跑的项目普遍存在 profile 无限膨胀
断点续爬 队列 + 每型号落盘 + 生命周期路由 + 崩溃恢复 多为"一次跑完，失败重来"
代理池 无（有意为之，见第 05 节） 有（LittleCrawler 多供应商、ShilongLee 时间片轮换）
数据质量闸门 三源过滤 + 平台集合 Jaccard ≥0.5 + 样本量闸门 几乎没有 —— 抓到什么存什么

05优化建议（按投入产出比排序）

P0取数方式：从 DOM 解析改为「网络响应截获」

现状问题：三个源都靠解析 innerText。京东依赖 [class*="goodsCardWrapper"] 这类模糊类名选择器，拼多多/闲鱼靠按行切分文本推断价格——平台改一次版就可能全线失灵，而且价格与标题的边界靠行序，本身就是脆弱假设。
建议方案：保留现有浏览器流程不动，只把取数那一层换成监听页面自己发出的 API 响应（page.on("response") / expect_response），DOM 解析作为兜底保留。
外部证据（已核对源码）：
· 闲鱼：页面调用 mtop.taobao.idlemtopsearch.pc.search，返回结构化 JSON（data.resultList[].data.item.main，含 title / price / area / userNickName / publishTime）
· 拼多多：页面调用 apiv3.yangkeduo.com 的 v4/operation/*/groups，返回 goods_list
· 京东：桌面搜索页是服务端渲染 HTML —— ⚠️ 2026-10-02 实测推翻：服务端 HTML 只有 47KB、零商品，商品数据在 api.m.jd.com/api?appid=search-pc-java 的明文 JSON 里（详见第 12 节）
预期收益：① 改版免疫（选择器失效风险→0）；② 可提前取数，响应到达即可解析，不必等整页渲染完成，单型号可省数秒；③ 拿到 DOM 上看不到的字段（发布时间、地区、卖家），可用于后续筛选。
成本与风险：改动限于取数函数，不动调度/熔断/生命周期。风险是接口返回字段名可能变动，需要开发时实测确认——这一条我尚未在本项目环境实测验证，属推断（依据是外部项目的抓取路径）。
建议验证顺序：先在闲鱼单个型号上试（收益最大），成功后再推拼多多。

这笔时间花在哪：拆开看，navigate + 显式首屏等待 + 滚动等待 2500ms + 行为模拟 + settle，页面渲染相关约 12~15s；其余是有意的拟人化间隔（这部分不能省，省了就是自找限流）。
可优化的是前者：用 P0 的网络截获后，命中搜索接口响应即可结束等待，不必等 SPA 把卡片渲染出来。
明确不建议的：不要自研 MTop 签名改走纯 HTTP。理由：签名规则会变，改一次就要重读源码；而"截获页面自己的响应"拿到的数据完全相同，却不承担签名维护成本。
可顺带借鉴：superboyyy 的单次重试策略 —— token 过期时刷新一次并重试，失败就直接返回，不进入循环。与我们"不撞墙"的原则一致。

P1拼多多 anti-content：若将来要脱离浏览器，用「签名机」而不是逆向

现状问题：我们目前不主动构造请求（浏览器自己发，签名天然正确），所以当前没有这个痛点。但拼多多是限流最重的源，若将来想做"轻量轮询"或提高频率，就会遇到必须自己签名的场景。
建议方案：采用路线 D —— 开一个官方页面，page.evaluate() 调它页面内的签名函数拿到 anti-content，再用 httpx 发请求。
证据：LittleCrawler 用这一方法处理小红书的 x-s 签名（window.mnsv2(...)），代码仅 226 行且不随平台改版失效。
对照：Crack-JS-Spider 的拼多多产物是 3717 行反混淆 JS + 补环境，2022 年产、补环境代码已注释、当前不可直接运行。
何时才做：仅当"必须主动构造请求"成为真实需求时。现在不做。

P2可观测性：用「分段计数」替代布尔判断

可借鉴的点：superboyyy 用三个计数 ws_frames（收到多少帧）/ sync_pushes（服务端推了多少次）/ parsed（解出多少条）来区分"没推到"和"推到了但没解开"——而不是笼统一句"连接失败"。
用在我们哪里：采集链路可以按同样思路拆：navigate 成功数 → 页面就绪数 → 命中数据接口数 → 解析成功数 → 入库数。这样"这个源今天数据少"能立刻定位到是哪一段漏了，而不是回去翻日志猜。
成本：很低。每轮结束在 summary 里多带一组计数即可。
为什么值得：我们已经吃过"跑了一整天 0 条没人知道"的亏（09-29 代理事故）。分段计数正是让这类故障在第一条日志里就现形。

P2熔断粒度：跨轮次指数退避

已知缺口（上一轮就发现了）：京东冷却 180s，而采集是每小时一轮 —— 冷却在下一轮开始前早就自然过期了，所以每个小时仍会去撞一次。
建议方案：连续 N 轮触发熔断 → 冷却时长指数拉长（180s → 30min → 2h）。判定依据落在 breaker.json 的 trips 计数上，改动很小。
对照：调研项目中没有跨轮次退避的实现（它们多是单次运行脚本，不存在"轮次"概念）。这一条是我们独有的场景，需要自己设计。

不做代理池 —— 评估后建议放弃

开源项目的做法：LittleCrawler 封装了极速/快代理/豌豆三个供应商的统一池；ShilongLee 按 5 分钟时间片轮换。
我们为什么不做：
  • 我们是带登录态的采集。代理一换，平台看到的是"同一个账号从不同 IP 高频访问"——这正是风控模型里账号盗用的典型特征，比固定 IP 更危险。
  • 目标站是国内的。用境外节点等于自己制造异常；用国内住宅代理则成本高、质量参差。
  • 收益不明确。当前限流的主要特征是"搜索级软风控"（登录态正常、搜索结果被降级），换 IP 未必能解决——这一点我们尚未验证，但"不确定收益 + 明确风险"足够支持不做。
什么时候重新评估：若京东/拼多多长期限流且已排除所有非 IP 因素（节奏、指纹、登录态），再考虑与登录态绑定的国内住宅代理。

不做多账号轮换 / 滑块脚本化 / 隐指纹补丁

  • 多账号轮换：需要多个实名账号。ShilongLee 支持多账号（/add_account），但它面向的是"账号越多越稳"的通用爬虫场景；我们是单一账号的价格追踪，多账号带来的合规与维护成本远超收益。不做。
  • 滑块验证码脚本化：LittleCrawler 有完整的缓动轨迹实现，wkunzhi 有滑块验证教学。但滑块是平台明确的安全控制，脚本化本身就是被检测的行为特征。我们现有策略（人工扫码 + 会话复用）是对的。不做。
  • 反指纹补丁（--disable-blink-features=AutomationControlled / stealth.min.js / JS 改写 navigator.webdriver）：这些针对的是 Selenium / Playwright.launch() 注入的自动化特征。我们是自己 Popen 启动普通 Chrome 再用 CDP 连接，本来就没有这些特征 —— 加上补丁等于主动断言"我在做自动化"。上一轮已有实测结论，不加。
  • --no-sandbox：LittleCrawler 加了，但这是 Linux 容器环境的习惯；macOS 上无必要且降低隔离性。不加。

09核对中发现的真实缺陷（建议优先修）

缺陷限流检测器把错误码当裸字符串搜正文 → 误熔断

现象：拼多多被判定限流并中止整批，但页面其实是正常搜索结果页。
证据 1 —— 命中位置（取自 data/collect.log）
23:31:33 拼多多 触发限流熔断：pdd 命中限流特征「40001」：想P3图形工作站台式机升级i9-14900K/128G/1TSSD /RTXA400016G 仅剩5件 24小时内发货 假一赔十 ¥ 35000 56人想拼 …
证据 2 —— 把 40001 定位回原文
判定命中的特征 '40001' 在被扫描正文的第 40 个字符处命中，上下文为：
…i9-14900K/128G/1TSSD /RTXA400016G 仅剩5件…
即显卡型号 RTX A4000 16G —— 「A4000」+「16G」拼出了 40001。
证据 3 —— 与真限流的形态对比（决定性）
今天拼多多共触发熔断数十次，真限流全部命中短语 系统繁忙，上下文格式统一为 「<型号> 商品 系统繁忙 请稍后再试」（平台内嵌的错误块）；
而仅有的 2 次（18:33:34、23:31:33）命中的是裸数字 40001， 上下文是带价格与"56人想拼"的真实商品卡片。两者形态完全不同。
根因：PLATFORM_THROTTLE_CONFIG["pdd"].rate_limit_indicators 里同时存在 'error_code=40001'（精确、安全）与 '40001'（裸数字）； 而 detect_rate_limit() 对 title + 正文 做的是朴素子串匹配 —— 正文里全是商品型号，数字串碰撞不可避免。
影响：① 每次误判中止整批（6 个型号 → 0 条）；② 推进软风控阶梯（15分 → 2小时 → 4小时）， 可能把本来正常的平台逐级锁死；③ 表现与"平台一直限流"无法区分，会误导后续所有判断。
建议修法（三步，都很小）：
  • 删掉裸数字 '40001' —— 它是冗余的，'error_code=40001' 已同时存在于 rate_limit_indicators 与 rate_limit_url_patterns
  • 加自检断言：任何平台都不允许出现"纯数字"的限流特征（钉住这一类，而不只是这一个）
  • 加真阴性用例：正文含 RTXA400016G 的正常商品页不得被判限流 —— 现有 3 个"真阴性"用例没覆盖到这种串
与既有教训的关系：这正是项目里第 1 条教训（"源码级断言只查子串一定不可靠"）的 生产版本 —— 同一个失效模式，此前只出现在测试里，这次跑进了判定逻辑。

10缺陷二：万元价被拆成多行渲染（数据污染级）

已修价格被拆成多行 → 2.30万 记成 ¥2.00

发现路径：核对缺陷一的过程中，注意到闲鱼库里价格上限恰好卡在 10000 （无一条超过），而同期京东有 66 条在 1 万~2 万。这个整数边界反常，顺着查下去就找到了根因。
证据 1 —— 库里的异常分布
平台1万~2万> 2万观察
闲鱼00上限恰好 = 10000
京东6613正常
拼多多4629正常
RTX 4090 24G 在闲鱼的 max 只有 9998，而它的二手实际行情是 1.3~1.6 万。
证据 2 —— 线上探针抓到的卡片原文（闲鱼搜索「RTX 4090 24G」，innerText）
华硕RTX4090+24G猛禽满血版… ⏎ 37分钟前发布 ⏎ ¥ ⏎ 2 ⏎ .30 ⏎ 万 ⏎ 1人想要 ⏎ 山西

价格 2.30万（¥23,000）被拆成三行。旧提取器只取「¥ 的下一行」= '2'， 而它通过了 /^\d+(\.\d+)?$/ 校验 → 记成 ¥2.00。 同一页 30 条里有 4 条中招。
（小数同样被拆：¥ ⏎ 18 ⏎ .88 → 记成 18 而非 18.88。）
为什么最终表现为"完全丢失"：¥2.00 这种假低价随后被 数据质量闸门判为离群值剔除 —— 所以库里看不到脏数据，只看到"某段价格凭空消失"。 脏数据能被发现，静默丢弃不能，这类 bug 因此格外隐蔽。
改法：新增 app/collectors/normalize.py。JS 退化为「原样取连续价格片段」 （priceSeg），拼装与判读全部交给 Python —— 因为 JS 里写不了单测。片段形状校验也在 Python： 首段必须是数字，后续段只能是 .xx 或 万， 遇到别的就停（否则「¥ 2688」后面跟一行「56人想拼」会被拼成 268856）。
验证 —— 改后用真实页面复跑
RTX 4090：30 行 → 16 条 ≥1万（改前 0 条），最高 ¥29,900，中位 ¥18,500
拆行价格 16 条，例：['2','.30','万'] → ¥23,000.00
⚠️ 数据影响：自 2026-09-16 起的闲鱼历史数据里，所有 ≥1 万的报价都缺失。 受影响的是旗舰显卡（4090 / 5090 / 5080）—— 它们的闲鱼均价被系统性低估， 性价比指数可能因此偏差。是否重采补齐需要单独决定。

二、两处「写了但不起作用」（已修 73be3e4）

已修① 第 1 级短于轮次间隔 = 空转

冷却是在下一轮开始时被 fast_fail() 评估的。 所以任何短于轮次间隔（1 小时）的冷却在调度上等于不存在 —— 到点一看早就过期了，照样全速去撞。第 1 级（硬 30 分钟 / 软 15 分钟）正是这种情况： 文档里写着「退避」，实际一轮都没跳过。
项目自己已经两次实测到这一点
· 2026-09-24 「15 分钟 < 轮次间隔，所以不跳过任何一轮」
· 2026-10-01 京东下午被拦 → 30 分钟冷却在下一轮早已过期 → 每小时继续撞
修法：新增 breaker.min_cooldown()，冷却取 max(阶梯级, 一轮 + 5 分钟缓冲)（默认 3900s = 65 分钟）。 只作用于阶梯路径 —— trip(seconds=...) 显式传值（单测/排障） 不套下限，否则秒级演练会被抬到 65 分钟。 DIYPRICE_BREAKER_MIN_COOLDOWN 可覆盖，设 0 回到阶梯原值。

已修② record_success 清零 → 间歇性拦截永远升不上去

原来一次成功就把余量清零。对「连续被拦」有效，但 对间歇性拦截完全无效：平台一小时被拦、下一小时侥幸采到几条 → 台阶被重置回第 1 级 → 永远升不到第 2 级。 净效果是每小时都全速撞同一堵墙，而阶梯一次没生效。
京东 10-01 正是这个形态（下午被拦、晚上 19:31 / 20:30 / 21:31 / 23:31 正常）， 当时 consecutive_trips("jd") == 0 就是被清零的直接证据。
修法：改为递减 —— 成功一轮减一级，减到 0 才整条清掉。 探针 verified=True 仍一次清掉（那是「渠道此刻可用」的直接证据， 不是侥幸）。
⚠️ 副作用：第 1 级软(15min)/硬(30min) 都被下限统一到 65 分钟， 软硬在第 1、2 级不再可区分。真正的区分从第 3 级开始 （软 4 小时 vs 硬 6 小时）。自检里原来「用第 1 级区分软硬」的断言已挪到第 3 级 —— 否则那两条断言会变成永远通过。

一句话总结

调研的 10 个项目里，最值得抄的不是它们的反爬手段，而是它们的取数通道 —— 数据在平台返回的 JSON 里， 而我们一直在解析渲染后的文本；同时它们普遍在工程化上远不如我们（无指纹实测、无熔断持久化、无磁盘治理、无数据口径闸门）， 所以正确姿势是只取"网络层取数"这一条，其余保持我们自己的做法。
